# أريد بناء نظام ويب داخلي احترافي Internal Order & Work Management System يعمل داخل شبكة الشركة...

أريد بناء نظام ويب داخلي احترافي Internal Order & Work Management System يعمل داخل شبكة الشركة المحلية LAN، ويكون الهدف منه إدارة الطلبات/المهام، العمال المرتبطين بكل طلب، المستندات والتواقيع، أوقات العمل، ومراحل إغلاق الطلبات، مع قاعدة بيانات مركزية ولوحة تحكم إدارية.

1. طبيعة النظام والبيئة التشغيلية

النظام عبارة عن Web Application داخلي وليس برنامجاً يتم تثبيته على كل جهاز.

يتم تشغيل التطبيق على Local Server داخل الشركة، وجميع أجهزة الموظفين المتصلة بنفس شبكة LAN تستطيع الدخول إليه من خلال المتصفح مثل:

- Google Chrome

- Microsoft Edge

- Firefox

مثال:

"http://192.168.1.100"

أو باستخدام Domain داخلي مثل:

"http://internal-system.local"

يجب أن تكون قاعدة البيانات مركزية، بحيث جميع المستخدمين يشاهدون ويعدلون نفس البيانات بشكل فوري.

يجب تصميم النظام بحيث يمكن نقله مستقبلاً من Local Server إلى Cloud Server بدون إعادة بناء النظام بالكامل.

2. الهدف الرئيسي للنظام

النظام مسؤول عن إدارة دورة حياة الطلب كاملة:

إنشاء الطلب → إدخال التفاصيل → تسجيل العمال → تنفيذ العمل → إرفاق المستندات → مراجعة الطلب → استكمال التواقيع والإثباتات → إغلاق الطلب → أرشفته.

يجب ألا يستطيع المستخدم إغلاق الطلب قبل استكمال جميع المتطلبات الإلزامية الخاصة به.

- تاريخ إنشاء الطلب

- تاريخ بدء العمل

- تاريخ انتهاء العمل

- حالة الطلب

- عدد العمال

- العمال المرتبطون بالطلب

- المستندات

- التواقيع

- ملاحظات

- المستخدم الذي قام بآخر تعديل

- تاريخ آخر تعديل

رقم الطلب

يجب أن يكون رقم الطلب فريداً ولا يتكرر.

مثال:

"ORD-000001"

"ORD-000002"

يجب عدم الاعتماد على رقم عشوائي فقط، بل يجب وجود Internal ID منفصل في قاعدة البيانات.

8. حالات الطلب Status

يجب أن يحتوي الطلب على Workflow واضح.

الحالات الأساسية:

1. مفتوح

"OPEN"

الطلب قيد العمل.

2. قيد التنفيذ

"IN_PROGRESS"

العمل جارٍ على الطلب.

3. بانتظار المستندات

"WAITING_DOCUMENTS"

العمل انتهى لكن المستندات المطلوبة لم تكتمل.

4. بانتظار المراجعة

"PENDING_REVIEW"

كل المتطلبات الأساسية تم رفعها والطلب بانتظار المراجعة.

5. مغلق

"CLOSED"

تم استكمال جميع المتطلبات واعتماد الطلب.

6. مؤرشف

"ARCHIVED"

الطلب مغلق وتم نقله للأرشيف.

ويجب عدم السماح للمستخدم بتغيير الحالات بشكل عشوائي إذا كان ذلك يخالف Workflow النظام.

---

9. شروط إغلاق الطلب Validation

هذه نقطة أساسية جداً.

لا يمكن إغلاق الطلب إلا بعد استكمال جميع المستندات والمتطلبات الإلزامية.

قبل السماح بالإغلاق يجب أن يقوم النظام تلقائياً بفحص:

- وجود رقم الطلب.

- اكتمال بيانات الطلب الأساسية.

- وجود العمال المرتبطين بالطلب.

- وجود توثيق رقم الطلب.

- وجود أوراق التواقيع.

- وجود إثبات عمل العمال.

- اكتمال أي مستندات إلزامية أخرى.

إذا كان هناك شيء ناقص:

يمنع النظام الإغلاق.

ويظهر للمستخدم مثلاً:

لا يمكن إغلاق الطلب. المتطلبات الناقصة:

❌ أوراق التواقيع

❌ إثبات عمل العمال

أما إذا اكتملت:

✅ جميع المتطلبات مكتملة

ثم يظهر زر:

إغلاق الطلب

12. Versioning للمستندات

أريد النظام أن يكون مرناً وقابلاً للتدقيق.

إذا تم استبدال مستند، لا تحذف النسخة القديمة مباشرة.

يفضل إنشاء Version History:

مثلاً:

"Signature.pdf — Version 1"

"Signature.pdf — Version 2"

مع تسجيل:

- من قام بالتعديل

- وقت التعديل

- النسخة السابقة

- النسخة الجديدة

بحيث يمكن معرفة تاريخ المستند.

19. حماية إغلاق الطلب

لا تعتمد فقط على إخفاء زر الإغلاق في الواجهة.

يجب أن تكون Validation موجودة أيضاً في Backend / Database Layer.

حتى لو حاول شخص إرسال Request مباشرة إلى API لتغيير:

"status = CLOSED"

يجب رفض العملية إذا كانت المتطلبات غير مكتملة.

هذه نقطة أمنية ووظيفية مهمة جداً.

---

20. منع فقدان البيانات

استخدم Database Transactions عند العمليات الحساسة.

مثلاً عند إغلاق الطلب:

1. فحص البيانات.

2. فحص المستندات.

3. فحص العمال.

4. التأكد من جميع المتطلبات.

5. تسجيل عملية الإغلاق.

6. تغيير حالة الطلب.

إذا فشل أحدها لا يتم تنفيذ الإغلاق بشكل جزئي.

34. حذف البيانات

لا تستخدم Delete نهائي للبيانات المهمة بشكل افتراضي.

يفضل استخدام:

Soft Delete

بحيث يتم الاحتفاظ بالسجل ويمكن للإدارة استعادته.

خصوصاً للطلبات والمستندات.

ويجب أن تكون عملية الحذف النهائي محصورة بالـ Administrator إذا كانت مطلوبة.

إذا حاول المستخدم إغلاق طلب ناقص:
